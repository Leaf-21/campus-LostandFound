# 03｜交互设计与视觉规范

> 本项目交互设计占总评 90%，本文件是成员 B 的核心工作依据，成员 A 在 API 和业务能力上必须配合。

## 1. 设计目标

呈现一个可信、温暖、清晰、轻量的校园互助服务，而不是普通后台管理系统。页面应使用户第一眼知道“这里可以找回丢失物品，也可以发布拾获物品”。主任务入口清楚，信息卡片易扫读，状态清晰，表单低负担。

## 2. 视觉方向

- 主色：深青绿 `#176B5B`，用于主按钮、选中状态和品牌识别。
- 辅色：薄荷浅绿 `#E8F4EF`，用于浅色背景和提示区。
- 强调色：暖橙 `#E98A45`，用于重点提醒和待处理状态，少量使用。
- 主文字：`#1F2A27`；次文字：`#65736E`；边框：`#E3EAE6`；页面底色：`#F7F9F7`。
- 成功：`#2E8B65`；警告：`#C9852C`；危险：`#C94C4C`；信息：`#4D7897`。
- 字体：优先系统中文字体栈；标题 24–32 px，卡片标题 16–18 px，正文 14–16 px，辅助说明 12–13 px。
- 圆角：卡片 14–18 px，按钮/输入框 8–10 px；卡片阴影轻，不使用厚重拟物效果。
- 图标统一 lucide 风格；禁止随意混用 Emoji 作为功能图标。

## 3. 页面结构和信息层级

### 3.1 首页 `/`

1. 顶部导航：品牌标识、首页、失物招领、发布信息、个人中心、登录/用户菜单。
2. Hero 区：一句清晰的价值说明 + 两个主 CTA：“寻找物品”“发布信息”。
3. 类型快捷入口：我丢失了 / 我捡到了。
4. 分类入口：证件卡类、数码产品、书籍文具、生活用品、衣物配饰、其他。
5. 最新信息：展示 6–8 张信息卡片；每张卡片显示类型标签、标题、图片、地点、时间和状态。
6. 页面底部：平台说明、互助安全提示。

### 3.2 信息广场 `/posts`

- 页面标题和简短说明。
- 顶部使用明显的 LOST / FOUND 切换标签。
- 搜索框支持 Enter 和搜索按钮触发；提供清空按钮。
- 筛选行：分类、地点、状态、排序；移动端收纳到筛选抽屉。
- 当前筛选条件用可删除 Chip 展示；提供“清空筛选”。
- 结果区显示结果数量、排序选择和卡片网格。
- 桌面端 3 列卡片（宽度不足时 2 列）；移动端 1 列。
- 分页置于列表下方；筛选条件变化时页码重置为 1。

### 3.3 信息卡片

卡片展示顺序：图片（固定比例）→ 类型/状态标签 → 标题（最多两行）→ 地点和发生时间 → 发布者昵称/发布时间。卡片整体可点击，但内部不再放多个竞争性按钮。图片缺失时显示统一占位图。卡片 hover 有轻微上浮或边框变化，避免夸张动画。

### 3.4 信息详情 `/posts/:id`

- 左侧/上方：图片画廊，主图清晰，缩略图可切换。
- 右侧/下方：类型、状态、标题、时间地点、分类、描述、酬谢说明、发布者摘要。
- 主操作区固定且突出：游客显示登录操作；非发布者显示“申请认领”或“提供线索”；发布者显示“编辑信息”和“查看收到的申请”。
- 处理中/已完成/已关闭状态应解释当前不能再申请的原因。
- 对危险动作或状态改变操作使用确认对话框。

### 3.5 发布/编辑 `/publish`、`/posts/:id/edit`

- 首先选择“我丢失了”或“我捡到了”，选择后标题和说明文案动态变化。
- 必填项：标题、描述、分类、地点、发生时间；图片可选最多 5 张。
- 标题 2–50 字；描述 10–1000 字；地点 2–100 字（与 API 契约 05 §8.3 一致）。
- 图片上传支持点击选择和拖拽；每张显示缩略图、上传状态、删除按钮。
- 提交按钮在提交中禁用；成功后跳转详情；失败保留用户已输入内容并显示错误。
- 表单不一次展示过多可选字段，酬谢说明为可选。

### 3.6 个人中心 `/me`

- 顶部用户卡片：头像/昵称/账号/资料编辑入口。
- Tab：我的发布、我提交的申请、我收到的申请。
- 我的发布按状态展示，并提供进入详情、编辑（仅 OPEN）等操作。
- 我提交的申请显示对应信息摘要、申请类型、申请状态、提交时间。
- 我收到的申请按 PENDING 优先展示；每条申请提供查看详情、接受、拒绝。
- 接受/拒绝/完成操作必须弹出确认，并显示执行结果。申请双方通过申请详情中的申请说明与处理备注沟通；首版不提供即时聊天。
- 空状态应提供下一步 CTA，如“去看看最新招领”或“发布一条信息”。

### 3.7 登录/注册

简洁居中卡片；突出当前任务；字段旁有校验提示；密码显示/隐藏；提交中有 loading；错误提示不暴露账号是否存在的敏感信息（注册冲突除外）。登录成功返回用户原本想访问的页面（如存在 redirect）。

## 4. 交互状态必须完整

每个异步页面/组件必须考虑：

1. Loading：骨架屏或按钮加载态，不允许空白闪烁。
2. Empty：解释为什么没有数据，并给出可执行下一步。
3. Error：友好错误说明、重试入口；不展示原始堆栈。
4. Success：明确成功反馈；必要时跳转或刷新数据。
5. Disabled：不满足条件时禁用按钮并解释原因。
6. Validation：字段级错误，不只在页面顶部显示总错误。
7. Confirm：接受申请、拒绝申请、完成归还、关闭信息等状态操作必须二次确认。
8. Duplicate prevention：提交期间禁用按钮，并在服务端校验重复申请。

## 5. 文案规则

- 使用真实、具体、友好的校园场景语言。
- 主按钮使用动词，例如“发布招领信息”“申请认领”“确认已归还”。
- 不用模糊文案如“提交”“确定操作”代替业务语义。
- 错误提示应告诉用户下一步怎么做。
- 英文枚举由前端映射为中文：`OPEN` 正在寻找/等待认领；`PROCESSING` 处理中；`RESOLVED` 已找回/已归还；`CLOSED` 已关闭；`HIDDEN` 已隐藏。

## 6. 可用性和响应式规则

- 桌面端内容最大宽度约 1200 px，主内容水平居中。
- 导航栏保持清晰，页面主操作在首屏尽量可见。
- 点击目标尽量不小于 40×40 px；表单 label 清晰，必填项有标识。
- 颜色不能作为唯一状态区分方式，同时使用文字标签。
- 键盘可聚焦主要操作，输入框有明显 focus 样式。
- 1366px 桌面端不出现横向滚动；390px 手机端不出现页面级横向滚动。

## 7. 组件清单（建议）

`AppHeader`、`AppFooter`、`HeroSection`、`PostTypeTabs`、`CategoryGrid`、`PostCard`、`PostGrid`、`PostFilters`、`FilterChips`、`StatusBadge`、`ImageUploader`、`ImageGallery`、`ApplicationFormDialog`、`ApplicationCard`、`EmptyState`、`ErrorState`、`LoadingSkeleton`、`ConfirmActionDialog`。

## 8. UI 验收标准

- 所有页面使用同一导航、色彩、字号、间距和按钮规范。
- 首页 5 秒内可理解平台用途，并明确找到寻物/招领入口。
- 列表筛选可见、可撤销、可清空；结果反馈即时且准确。
- 详情页重要信息先于辅助信息，主操作不会被淹没。
- 发布流程字段清楚，错误提示出现在对应字段附近。
- 个人中心能一眼区分“我发布的”“我发出的申请”“别人发给我的申请”。
- 所有页面均包含加载、空、错误和成功反馈。
- 使用真实演示数据和清晰图片；避免大面积空白、错位和默认组件风格堆叠。
